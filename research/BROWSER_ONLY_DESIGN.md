# 鸣潮 XP 排行榜：纯浏览器更新方案

更新时间：2026-10-23。

2026-10-24 微调更新：同步改为仅在每次打开时检查，距离上次拉取超过24小时才执行；取消前台切换轮询与用户同步入口。评价、分级、收藏已从界面移除，备份改用名称。当前产品行为以 README.md 为准；下文保留原方案记录。

根据用户最新约束，推荐将运行方式收敛为纯前端：平时自动取得可公开读取的资料，允许偶尔由用户和 agent 维护项目；现阶段按上游接口与内容结构保持现状设计。

这是设计建议及浏览器验证记录，不是已完成的产品。无需承诺任意上游变化都自动适应。

## 最小组成

```text
静态 H5
  + 浏览器直连 Wiki 的资料读取与解析模块
  + IndexedDB 本地缓存与个人排名
  + 项目附带的一份基础资料及已确认头像映射
```

网页文件放在普通静态 HTTP(S) 托管上，用户打开地址即可使用。静态托管只负责提供文件，不需要业务后端、服务端数据库或后台定时任务。开发调试可以用本地静态服务器。

本方案不以双击 `file://` 页面作为运行承诺；该环境的 Origin、模块和存储行为需要另行验证。正式部署地址仍须做一次实际浏览器跨域验收。

## 已在真实浏览器验证的部分

使用只有 HTML/JavaScript 的临时静态页面，从 `http://127.0.0.1:8783` 直接发起 `fetch`，全部显式设置 `credentials: "omit"`。本地服务器没有转发官方 API。

- Wiki 分类树：浏览器成功读取，HTTP 200、业务 code 200。
- Wiki 共鸣者目录：浏览器成功读取 65 条记录。
- 今汐详情：浏览器成功读取基础信息、皮肤、档案、故事和两类语音数据。
- 社区头像列表：浏览器能够读取错误响应，但业务 code 220，提示“访问令牌不能为空”。此处是鉴权门槛。
- 攻略站目录：浏览器 `Failed to fetch`。补充 HTTP 请求确认其 OPTIONS 和 GET 均未允许这个测试 Origin，不能把它作为本方案运行时更新的必要依赖。已有图片链接仍可用于素材补缺。

具体结果见 [browser-access-evidence.json](browser-access-evidence.json)。

## 日常自动更新流程

1. **打开即展示。** 优先读浏览器中最近有效的资料与个人排名；首次访问时用项目附带的基础资料，避免等所有接口返回才显示页面。
2. **按过期时间检查目录。** 页面打开、恢复到前台或用户点击刷新时，检查是否需要更新。建议起步阈值为 6 小时，具体值在实现时确定。
3. **新增角色优先。** 读取新条目的详情、皮肤和所有实际提供语种的音轨索引，进入待排名集合；没有独立头像时按已有素材和缺项规则显示。
4. **旧角色也复查。** 目录没有新增时，仍低并发更新到期的角色详情，以捕获后补语音、皮肤和故事。用户正在看的角色优先处理。
5. **逐角色保存有效结果。** 请求及解析检查通过后再更新该角色缓存；失败保留最近有效内容。每条记录保存同步时间，未完成的记录下次继续，不必维护复杂的数据版本发布系统。

页面持续打开时可以低频检查；不要依赖后台标签页定时器准点执行，以页面打开和回到前台的过期检查为主。6 小时是更新条件，不是浏览器关闭后仍然执行的计划任务。

**明确边界：网页关闭期间不保证同步。** 重新打开以后检查并补齐，即使数月没有打开也按当前来源目录发现新条目。每个浏览器自行缓存和刷新，这不是全站共用的服务器数据。

## 数据与媒体

- 基础资料、完整档案和故事、珍贵之物、皮肤资料以及语音标题/台词/URL 存入本地资料缓存。
- 图片和音频继续引用原始 URL，按实际查看和播放加载，不预先下载全部立绘或 WAV。
- 项目附带的基础快照主要用于首次加载和请求失败兜底；每次人工维护时更新一次即可，正常资料更新不依赖重新发布该快照。
- 新内容以来源实际公开的内容为准。其他语言或皮肤素材暂未提供时保留缺项状态，后续刷新继续补充。
- Wiki 请求、响应解析和字段映射集中维护，界面只消费整理后的数据。
- 目录返回的长 ID 在本次浏览器测试中是 JSON 数值；需要无损解析并转为字符串，不能先用普通 `JSON.parse` 丢失精度后再补救。
- 解析上游图文时保留正文结构和资源链接，同时清理不适合执行的 HTML；未知栏目不能静默变成“没有内容”。

## 个人 XP 排名

个人排名、喜爱程度、理由与官方资料分开保存。资料刷新不覆盖这些偏好，新角色先进入待排名集合。

提供简单的 JSON 导出与导入，方便备份和换浏览器。浏览器存储不等于云端同步，清理站点数据后需要从备份或项目附带资料恢复。

如果后续需要让其他人打开链接看到同一份个人榜单，可以选择随站点发布一份公开排名，或分享可导入的排名数据；具体分享方式留到页面设计阶段确定。不能把某一浏览器的本地排名误当作所有访客的共享数据。

## 社区头像的简化处理

登录态是取得新社区头像目录的主要门槛。另外，上一轮观察到的选择器未给出角色名，图像候选仍需要确认；这两个问题在定期人工维护下可以收敛为小范围更新。

- 日常继续使用已确认的角色到高清头像 URL 映射。
- 新角色先自动使用 Wiki 中能够可靠关联的头像；之后确认更高清素材时再替换。已知图片直链不需要为每次显示重新获取头像列表。
- 用户与 agent 定期维护时，通过用户正常可访问的官方页面补齐新头像，并核对对应角色，只更新映射数据。
- 本方案不建设自动登录、Token 续期或无人值守图像识别，不要求将个人凭据放入 H5。

## 每两个月左右的人工维护

维护内容可以保持集中：验证目录/详情接口是否可用，检查新角色与皮肤能否解析，补齐高清头像和少量特殊关联，更新基础快照，做一次浏览器验收。

这是用户设想的维护节奏，不是新建的提醒或定时任务。没有异常时通常是数据补充；来源调整访问规则或内容结构时，才修复集中维护的解析模块。

## 复杂度取舍

相较此前“后台采集再发布远程 JSON”的选项，本方案省去了后台调度、数据发布服务、账号体系和多版本回退平台。保留的本地缓存、基础快照和请求失败时使用旧资料，是让一个个人 H5 平时可用的基本措施。

采用这一方案的条件是接受：更新发生在页面运行期间；头像质量可能先用可用素材、再人工提升；上游出现破坏性改动时，偶尔由用户和 agent 修复项目。

此前 [SYNC_FEASIBILITY.md](SYNC_FEASIBILITY.md) 的匿名接口实测仍有效；其中后台定时采集架构作为需要“无人打开也持续同步”时的备选，不再是当前推荐主线。
