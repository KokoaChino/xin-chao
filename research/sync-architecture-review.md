# 自动同步架构评审

评审日期：2026-10-23。

本文件根据当前 research 素材与范围做设计评审，不代表已实现同步服务，也没有创建定时任务。接口是否仍可匿名调用由本轮独立在线复测确认；本文件不把旧快照当作当前接口可用性的证明。

## 结论

常规版本新增角色、给已有角色补充皮肤、档案、语音时，可以通过自动同步数据让 H5 更新，而不需要修改前端代码或重新发布前端。整体属于中等难度的数据采集与发布工程。

全部来源长期无人工干预、所有新头像自动准确匹配，以及任意 Wiki 编辑结构变化后仍能完整提取，难度明显更高。不能把“不需要随每个版本手动发版”承诺为“永远不需要维护”。

## 当前数据中的实际约束

- `wiki-findings.md:24-82` 已记录角色目录和详情的公开读取方式，并记载之前没有使用凭据。当前匿名读取是否仍成功，应以本轮复测为准。
- `wiki-findings.md:16-22` 显示 65 条来源记录包含男女漂泊者属性条目、角色形态及预告；58 个身份组只是候选，不等于已确定的排名身份规则。
- `community-avatar-findings.md:23-25` 显示头像选择器没有暴露角色名。当前 58 张头像是算法生成候选后逐张目视确认，其中 8 张纠正过算法候选。即使解决登录态，也不自动解决角色关联问题。
- `MATERIAL_SCOPE.md:50-63` 明确完整档案、珍贵之物、故事、全部语种与战斗语音仍未补采完成。锁暝页面的其他语种暂为空白占位，不能把四语种 CV 列表当作四套音轨。
- 当前五位角色的皮肤在 `角色皮肤`、`皮肤立绘` 两类组件中分别出现。不能把它们当作两套不同皮肤，也不能只读取主立绘数组就认为皮肤已完整覆盖。
- `assemble-assets.py` 是合并已有快照的研究脚本，尚非具备持续发现、抓取、验证、发布、回退能力的同步器。

## 最小可用方案

数据链路：

```text
定时运行的采集程序
    -> Wiki 目录和详情 / 补缺来源
    -> 解析角色、皮肤、语音与图片元数据
    -> 与上次成功结果比较并验证
    -> 发布远程 JSON
    -> H5 在运行时读取 JSON
```

1. 从来源目录发现条目，按返回总数分页读取，不依赖当前角色数组或单次大 limit 永远足够。
2. 同步已有角色详情，而不只检测新增角色。皮肤、其他语种和故事可能晚于角色上线才补齐。
3. 将基础信息、档案段落、图片、皮肤、音轨转换为稳定的数据结构，H5 用通用组件渲染。
4. 图片与音频仍使用原站 URL。远程 JSON 存索引、文本及验证元数据，不需要把全部媒体文件纳入项目。
5. 首轮可采用低频全量角色详情同步，内容哈希用于发现变化；优先复查近期新增和仍有缺项的记录。无需先建设复杂数据库或消息队列。
6. 检验成功后发布一个新的数据版本，并切换当前版本指针。发生请求失败、异常空目录或解析错误时继续提供上一次成功版本。
7. H5 显示资料最后成功同步时间。缓存应能再验证或有合理有效期，避免 JSON 永远停留在旧缓存。

这需要一个能按时运行程序并写入数据存储的环境。H5 页面本身可以保持静态托管；浏览器关闭以后不能依靠这个页面执行后台定时抓取。定时任务更新 JSON 与重建前端应用是不同的事情。

将 `asset-manifest.json` 直接 import 进前端构建产物，会把数据固定在当次构建里。要实现用户希望的无需前端发版，应在运行时 fetch 可更新的数据地址。具体采用哪种托管与调度平台，留到实现时依据实际部署环境选择。

## 数据更新不能覆盖个人 XP 排行

- 官方资料与个人排名、喜爱理由、收藏分开保存。
- 排行记录引用稳定的内部角色身份 ID。Wiki 条目 ID、攻略站角色 ID、角色形态和皮肤 ID 作为关联信息保留，避免把显示名称当作主键。
- 来源长整数 ID 全程按字符串处理；前端转为 Number 会丢失精度。
- 新角色进入待排名集合，已有角色的排名和个人文字保持不变。自动抓取无法判断用户对新角色的喜爱程度。
- 新属性、新形态、皮肤与原角色的归属需能表达为关系，不随目录顺序变化重新分配 ID。已确认的别名和关联表应跨同步保留。
- 对未确认归属的新形态先保留独立来源条目，不因名称相似擅自合并。最终是否单独排名属于产品规则，仍待后续确认。

## 头像自动化的实际取舍

建议把带名称和来源 ID 的 Wiki 头像作为自动更新基线，同时保留现有已确认的高清头像映射。攻略站可作为后备来源。

社区头像可以作为质量增强来源：已知 URL 继续使用；新头像必须先取得可靠角色关联。图像相似度只能生成候选。低置信度时继续使用带名备用图，并把高清头像提升列为待核验，不因这一处缺项阻塞角色资料上线。

若要求每个未来新角色都立即使用社区选择器的最高质量头像、且完全无人核验，必须先解决登录列表获取及无名图片准确关联这两个独立问题。当前资料不支持宣称已解决。

## 长期可靠方案比最小方案多什么

- 按来源隔离解析逻辑，保留原始响应或来源结构摘要，便于结构变化后修复和重新解析。
- 按角色、栏目、语言记录完整性和抓取状态。区分来源暂未提供、请求失败、结构未知和已成功收录。
- 自动读取来源实际存在的语种，不把音轨语言上限写死为四种，也不把中文台词冒充其他语种台词。
- 皮肤按名称和稳定来源关系归组，合并跨组件的说明、海报、编队立绘与专属音轨；保留未知类别供后续解析。
- 跟踪预告、实装与未知状态，不把 `showTeaserIcon` 单独当作尚未实装的依据。状态不能可靠判断时如实展示未确认。
- 对新增或变化的媒体验证可访问性、真实尺寸和基本解码；复用未变化资源的已验证结果。像素尺寸足够不等于人物裁切一定美观，无法自动推导出的裁切保持通用展示或等待人工修正。
- 只删除具有明确删除证据的数据；单次目录缺失或抓取失败不清空历史内容。记录变更日志、失败原因和最近成功时间。
- 采用带版本的快照、发布前检查和回退能力。若上游仍可访问但字段大面积缺失，停止发布异常版本并保留上次正常数据。
- 前端通过受控文本和内容节点渲染来源图文，不直接把未知 HTML 原样执行。

## 难度拆分

| 目标 | 难度判断 | 原因 |
| --- | --- | --- |
| 在已验证匿名读取基础上发现新角色和更新主要资料 | 中低 | 已有目录与详情结构线索，工作集中在完整提取与数据整理 |
| 全档案、珍贵之物、全部语种、皮肤的通用解析 | 中等 | 组件布局并非单一固定字段，需要覆盖不同角色页面并保留缺项语义 |
| 定时发布远程数据，前端无需随内容更新发版 | 中等 | 技术路径直接，但需要调度、存储、校验和失败回退 |
| 社区新头像自动取得并始终准确对应角色 | 较高 | 登录态与无名图片关联是两个不同障碍，已有算法也出现过误匹配 |
| 多来源长期稳定、结构变化自动适应且完全零维护 | 不应承诺 | 上游没有在当前资料中提供稳定第三方 API 合约，编辑结构、访问要求与媒体链接都可能变化 |

推荐以 Wiki 为可持续同步主线，把个人排名与资料彻底分离；社区高质量头像作为可降级的增强项。这样能满足版本更新自动呈现的核心目标，同时不让最难的一类素材决定整个系统是否更新。
