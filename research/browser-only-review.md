# 纯前端自动更新方案评审

日期：2026-10-23，Asia/Shanghai。

本评审只读取现有研究资料，没有联网复测，没有实现前端、创建后台任务或部署服务。现有匿名请求及跨域记录见 `sync-wiki-assessment.md` 与 `sync-access-evidence.json`；最终部署来源的浏览器直连能力仍应单独验收。

## 结论

按“官方接口暂时维持现状，用户约每两个月配合 Agent 维护一次”的约束，可以采用静态 H5，在浏览器中直接读取公开 API，免去常驻后端、服务端数据库和后台定时发布流程。官方角色资料更新与前端发布可以分开：正常打开页面即可获取新内容；人工维护时更新解析器、头像映射和随项目提供的基础数据。

必须解释的边界是：自动更新只在页面获得运行机会时发生。浏览器关闭、系统休眠或页面长期处于后台时，不保证执行采集；下次打开页面或回到前台再检查。各浏览器分别缓存读取到的内容，不会产生一个由所有访问者共享写入的公共数据文件。

## 保持最少的组成

```text
静态 H5
  ├─ 基础快照：首次访问或尚无缓存的兜底资料
  ├─ 官方公开 API：目录、角色详情及素材 URL
  ├─ IndexedDB：最近通过校验的角色资料、同步时间
  └─ 个人数据：XP 顺序、喜欢理由、展示偏好
```

基础快照和缓存不是两个持续发布的数据系统。基础快照只提供保底；缓存保存本浏览器已获取的更新。没有必要建立全量版本历史、发布指针、任务队列服务或媒体镜像。每个角色更新校验通过以后，用一次本地事务替换该角色记录即可。

开发实现可集中为三类模块：

- `sources/wiki`：所有官方请求、组件解析、长 ID 的无损处理及素材链接规范化。
- `data/characters`：基础快照、IndexedDB 读取、过期检查、重试与更新合并。
- `data/preferences`：个人排序和喜爱理由，与官方资料独立存储及导入导出。

头像人工修正单独保留一个小映射文件，以稳定角色 ID 关联官方图片 URL；不要散落在界面组件中。

## 页面运行时如何更新

1. 首屏先使用本地已验证数据，首次访问则使用基础快照，不阻塞整个界面等待几十个请求。
2. 页面打开、重新进入前台或用户点击“更新资料”时检查目录。可先设置六小时的检查间隔；这是去重和节流策略，不承诺页面关闭时六小时执行一次。
3. 发现新条目后优先取得详情，新增角色进入待排名。对归属不明确的新形态保留来源记录，不擅自合并到旧角色。
4. 打开角色详情时，过期内容优先刷新。已有角色也进入低并发的过期复查流程，以发现后来增加的皮肤、故事或其他语言语音。不能只抓新角色，也不能只相信目录日期。
5. 分批处理并保存完成状态；页面中断后下次继续。无需一次打开就下载所有历史响应或所有媒体。
6. 请求失败、业务码异常或解析结果明显缺失时继续使用之前的有效记录，展示上次成功时间。单次目录缺失不删除用户已有的排名项。

无需为了这一要求引入 Service Worker 或后台同步能力。它们不能作为“关闭页面后永久按时抓取”的保证。

## 完整素材不等于预下载全部文件

角色资料保存完整文字及图片、音频链接。所有实际可获取语种和皮肤都进入元数据结构；空语言栏目与“敬请期待”记录为来源暂缺，不伪装为已有音频。

头像与当前屏幕需要的立绘按需加载；完整图片通过浏览器正常图片缓存复用。音频在用户播放时再加载，避免把每个角色的所有 WAV 文件预下载。皮肤按角色、名称和来源关系归组，合并“角色皮肤”和“皮肤立绘”的对应内容。只有真实存在的专属音轨才标为皮肤语音。

源站 HTML 应转换为受控段落和图文节点，或清理后渲染；不要直接执行源站 HTML 中的脚本及事件属性。

## 社区头像如何简化

现有记录表明社区列表要求 token，同时头像选择器没有角色名称。两者是独立问题；先前图像候选中有 8 张需要人工纠正。

在定期人工维护前提下，没有必要自动登录、保存用户 token 或研发复杂识别：

- 继续使用已经确认的高清头像映射；已知图片 URL 的读取与目录登录是不同环节。
- 新角色使用能通过来源名称或 ID 可靠关联的 Wiki 头像；使用经过验证且允许跨域读取的补缺来源。
- 每两个月维护时，由用户在社区正常登录，Agent 辅助核验新增图片，补充映射和新快照。
- 某张社区头像暂时无法更新，只影响头像清晰度提升，不阻塞角色资料和皮肤语音更新。

## XP 排行保存与分享

个人偏好按稳定角色身份保存，不按数组位置、显示名称或素材文件名关联。官方更新不覆盖排名和喜欢理由，新角色先待排名。

浏览器数据可能被清理，也不会天然跨设备同步，因此首版应有一个简单的 JSON 导出和导入入口，备份排名和偏好即可，不需要包含所有媒体。换域名也应视为换了一份浏览器存储。

若成品还需“别人打开链接就看到我的榜单”，静态站可带一份公开的初始排行榜，或另外实现分享文件/分享链接；不能把本机 IndexedDB 当作所有访客都能读取的共享数据。具体分享体验属于后续界面及产品规则，不是本轮新增后端的理由。

## 浏览器运行的含义

推荐“部署为普通静态 HTTP(S) 页面，用户点链接打开”。静态文件托管不等于常驻业务后端；开发时使用本地 HTTP 服务。

“双击本地 HTML，以 `file://` 打开”是另一项兼容性要求，涉及本地资源、Origin、模块和存储行为，不能当作与静态站相同的运行条件。现有跨域记录不能替代这项验收，也不能据此承诺任意浏览器都可从本地文件读取官方 API。

纯前端实时读取能否工作最终取决于源站允许目标网页来源跨域访问。应在实际浏览器和目标部署来源验证；若未来源站关闭该能力，前端无法自行改变源站策略。此时仍保留上次成功数据与基础快照，等定期维护再处理。

本方案不要求用户安装扩展、复制凭据、关闭浏览器安全限制或使用第三方 CORS 代理。
