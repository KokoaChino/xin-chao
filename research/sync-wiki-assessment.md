# 官方 Wiki 自动同步可行性实测

核验日期：2026-10-23（Asia/Shanghai）。本次仅评估，不实现生产爬虫，也不建立定时任务。

## 结论

目前所需的公开目录和角色详情接口可以匿名读取。目录发现、新角色识别、档案和皮肤解析、来源实际提供的音频链接同步具备技术可行性。登录态不是本次实测的阻碍，但这些是网站使用的接口，没有获得稳定性承诺，不能据此保证永久无需维护。

自动发现新角色相对简单；持续补齐已有角色的皮肤、语音和故事，以及在来源改版时保留正确的旧数据，是需要重点设计的部分。

## 无登录请求验证

所有请求都通过 `curl -q` 发出，禁用本机 curl 配置；只显式设置以下三个请求头：

```text
Content-Type: application/x-www-form-urlencoded
wiki_type: 9
source: wiki
```

没有提供 Cookie、登录 token、Authorization，也没有复用浏览器会话。没有调用编辑、上传或任何写入接口。

| 读取对象 | 接口 | 表单内容 | HTTP | 业务 code |
| --- | --- | --- | --- | --- |
| 目录树 | `POST /wiki/core/catalogue/config/getTree` | 空表单 | 200 | 200 |
| 共鸣者目录第 1 页 | `POST /wiki/core/catalogue/item/getPage` | `catalogueId=1105&page=1&limit=5` | 200 | 200 |
| 共鸣者目录第 2 页 | 同上 | `catalogueId=1105&page=2&limit=5` | 200 | 200 |
| 今汐详情 | `POST /wiki/core/catalogue/item/getEntryDetail` | `id=1249040336606580736` | 200 | 200 |
| 锁暝详情 | 同上 | `id=1543075487722901504` | 200 | 200 |
| 赞妮详情 | 同上 | `id=1309607355563974656` | 200 | 200 |

API 域名为 `https://api.kurobbs.com`。以上六次都返回 `success: true` 和 `msg: 操作成功`。响应的服务器日期均为 2026-10-23。完整请求摘要和经过筛选的结构证据位于 `sync-wiki-evidence.json`，不包含正文全文、编辑者资料或用户评分数据。

可复现示例：

```sh
curl -q 'https://api.kurobbs.com/wiki/core/catalogue/item/getEntryDetail' \
  -H 'wiki_type: 9' \
  -H 'source: wiki' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'id=1249040336606580736'
```

## 自动发现与分页

目录树提供 `name`、`id`、`parentId`、`children`，可以沿 `全部 / 游戏图鉴 / 共鸣者` 找到目录 `1105`；沿 `全部 / 游戏图鉴 / 头像` 找到目录 `1363`。因此不需要预先写死未来每一个角色 ID。目录名称和树形结构本身仍是上游依赖，改变后应让同步报出结构变化，而不是静默选择错误分类。

本次目录第一页得到 65 条记录、65 个不同 `entryId`，可以将其与本地已有 ID 集合比较，识别新条目。这里的 65 是图鉴记录数，包含属性/形态条目，不等于独立角色数。

分页有一个值得保留的实测细节：

- 请求 `limit=5`，服务端实际返回 `size=1000`。
- 第一页返回 65 条，`current=1`、`pages=1`、`total=65`。
- 第二页返回 0 条，`current=2`、`pages=1`、`total=65`。
- Wiki 公开入口脚本 `index-cb566e5b.js` 自己发送 `page: 1, limit: 1000`；它的 `transformRequestParams` 没有改写分页参数名称。
- 未证实该接口支持可控的小页大小，不猜测 `pageSize` 等参数。正式同步应遵循响应的分页元数据，校验总数和重复 ID，并为后续超过一页保留适配与验证。

## 增量字段能做到什么

目录返回 `catalogPageVersion` 和 `catalogPageVersionOnline`，本次均为 `199.0`；树根的对应值为 `403.0`。卡片 `content` 中有 `updateAt`，详情有 `currentVersion`、`onlineVersion`、`lastUpdateTime`。

| 样本 | 详情 currentVersion / onlineVersion | 详情 lastUpdateTime | 卡片 updateAt 按 Unix 毫秒转换为北京时间 |
| --- | --- | --- | --- |
| 今汐 | `60.0 / 60.0` | `2025-12-29` | `2026-08-20 05:04:48.086` |
| 锁暝 | `22.0 / 22.0` | `2026-10-22` | `2026-10-22 10:23:14.759` |
| 赞妮 | `22.0 / 22.0` | `2026-04-29` | `2026-10-09 11:08:32.018` |

这些字段可以保存为变更线索，但不能直接当作可靠的增量游标：

1. 卡片日期与详情日期并不等同，卡片改动可能只涉及展示配置；本次未证明它覆盖档案、子组件或音频变更。
2. `lastUpdateTime` 只有日期，无法区分同一天的多次修改。
3. 版本字段的单调性、覆盖范围没有公开契约，也没有跨真实编辑事件验证。
4. 详情版本在取得详情之后才可见，本次没有发现独立的轻量变更清单。
5. 本次响应没有可用于条件读取的 `ETag` 或 `Last-Modified`，并返回 `Cache-Control: no-cache, no-store, max-age=0, must-revalidate`。这只是响应中的缓存指示，不说明平台对第三方资料存储和再展示的许可范围。

稳妥方案是定期刷新角色目录，立即读取新 ID，并以较低频率轮询已有角色详情；对本项目需要的字段做规范化和内容哈希，只有发生变化才发布新的站点数据。哈希应排除浏览量、编辑者资料和播放器状态等无关波动。此处的哈希减少无谓发布，不等于减少全部详情请求。版本号和卡片日期可以帮助调度优先级，不能独立决定永久跳过旧角色。

## 皮肤、正文与语音结构

三份详情都在 `data.content.modules[].components[]` 下提供内容：

- 基础信息、主立绘：`type: role-component` 下的 `role`。
- 档案说明：`basic-component` 的 HTML 字符串。今汐的标题是“检验鉴定”，锁暝是“共鸣能力鉴定报告6hz”，赞妮是“共鸣能力鉴定报告”，不能只写死一个标题。
- 珍贵之物、角色故事：`tabs-component` 的 `tabs[].title` 和 `tabs[].content`；三份样本均有 4 项珍贵之物、5 篇角色故事。
- 今汐、赞妮均有“角色皮肤”和“皮肤立绘”组件，分别收录“桃夭灼灼”“城市午茶”。内容是带图片和文字的 HTML，并非统一的皮肤对象数组。
- 语音：`audio-component` 的 `mediaTabs[].mediaList[]`，其中有 `id`、`audioTitle`、`content`、`playUrl`、`fileSize`。应仅提取内容所需字段。

目前三份样本的音轨数量：

| 样本 | 中文个性语音 | 中文战斗语音 | 日文 / 英文 / 韩文 |
| --- | ---: | ---: | --- |
| 今汐 | 31 | 43 | 三种均为“敬请期待”空数组 |
| 锁暝 | 30 | 41 | 三种均为“敬请期待”空数组 |
| 赞妮 | 31 | 39 | 三种均为“敬请期待”空数组 |

这不表示游戏只有中文语音，也不表示所有角色的 Wiki 都只有中文；仅说明本次三份详情实际提供的音频链接为中文。四语种 CV 信息和四语种可播放音轨必须区分。自动同步应遍历全部语种标签，收录真实非空的 `playUrl`，空栏目记录为来源暂缺；如果未来补上其他语言，下一次刷新即可自动补齐。本次只核对音频链接字段，没有下载或播放音频。

解析器需要兼容嵌套 HTML、不同栏目标题、缺失组件和后续新增组件。正文导入时应保留合理段落结构并清理上游 HTML；无法识别的结构要记录并告警，避免把空解析结果发布成“角色没有皮肤/没有故事”。

## 实施边界

这次结果支持“数据自动跟随上游公开资料更新”，不支持“永久零维护”承诺。每次新版本正常沿用结构时，不必人工修改角色名单或重新写前端；若接口改地址、调整访问校验、组件结构变更或资料暂缺，仍需要来源适配或等待补齐。源站没有的内容，采集程序无法凭空生成。

同步服务应保存最后一次通过校验的数据，新数据异常时继续提供旧版，并展示准确的最后成功同步时间。新角色进入“待排名”区，用户自己的喜爱排序与上游角色资料分开保存，避免更新资料时覆盖个人 XP 排名。
