# 鸣潮角色素材自动同步：可行性评估

评估日期：2026-10-23，Asia/Shanghai。

方案更新：用户后续明确希望浏览器直接运行、减少系统复杂度，并接受约每两个月人工与 agent 维护。当前推荐改为 [BROWSER_ONLY_DESIGN.md](BROWSER_ONLY_DESIGN.md) 中的浏览器直连和本地缓存方案，已补充真实浏览器验证。本文保留接口调查及后台定时同步选项，后者不再是当前推荐主线。

用户目标：游戏发布新版本、新角色或皮肤以后，项目可以自行取得来源站点更新的资料，常规内容变化不需要人工修改角色列表、重建或重新发布 H5。

本轮只进行了匿名只读请求和架构评估，没有实现生产采集器、部署服务或创建定时任务。

## 结论

可以实现，整体属于中等难度。当前核心 Wiki 读取接口可以匿名访问，登录态不是本次验证中 Wiki 自动同步的前置障碍。

可实现的目标是：在来源站点公开新资料以后，通过定时同步发布数据，让 H5 自动出现新角色或更新旧角色资料。不能承诺游戏更新后立即拥有尚未公开的素材，也不能承诺上游接口、鉴权规则或内容结构改变后永远不需要维护。

本项目最明显的自动化缺口是社区高清头像：目录要求 token，而且已观察到的头像选择器没有角色名称。上一轮有 8 个图像匹配候选需要人工纠正。这个问题应有备用来源，不能成为整个站点更新的前提。

## 本次匿名访问实测

所有请求使用独立的 `curl -q` 进程，禁用 curl 配置文件，没有携带 Cookie、token、Authorization 或浏览器会话。

| 请求 | 实测结果 | 对同步的意义 |
| --- | --- | --- |
| Wiki `catalogue/config/getTree` | HTTP 200，业务 code 200 | 可以读取分类树，动态定位“游戏图鉴 / 共鸣者”和“头像” |
| Wiki `catalogue/item/getPage` | HTTP 200，业务 code 200；第一页返回 65 个不同条目 | 可发现新条目，不需要把当前角色名字固定写入代码 |
| Wiki `catalogue/item/getEntryDetail` | 今汐、锁暝、赞妮均 HTTP 200，业务 code 200 | 可以读取档案、立绘、皮肤及语音记录 |
| 社区 `/user/head/list?type=1` | HTTP 200，但业务 code 220，`访问令牌不能为空` | 头像列表目前要求登录凭据；不能只凭 HTTP 200 判定采集成功 |
| 攻略站 `/role/avatar/list` | HTTP 200，业务 code 200，60 条目录记录 | 可以作为角色索引与图片的后备来源 |
| 已知社区头像原图、Wiki 音频 | 匿名 Range 请求均 HTTP 206，分别返回 PNG、WAV 文件头 | 已取得的公开媒体链接可以独立加载，目录鉴权不等于文件也要求登录 |

Wiki 复现示例：

```sh
curl -q --silent --show-error \
  'https://api.kurobbs.com/wiki/core/catalogue/item/getEntryDetail' \
  -H 'wiki_type: 9' \
  -H 'source: wiki' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'id=1249040336606580736'
```

请求仅使用来源页面读取资料所用的分类、来源和表单字段，没有个人登录凭据。

跨域也做了单独的 HTTP 层探测：Wiki 详情请求携带 `Origin: https://example.com` 时返回了匹配的 `Access-Control-Allow-Origin`；相应 OPTIONS 请求允许 `POST` 及 `source,wiki_type` 请求头。因此不能简单认定“浏览器直连一定因 CORS 失败”。这不是对最终部署域名的浏览器端完整验收。

## 推荐的数据链路

```text
官方 Wiki 与补缺来源
    -> 页面以外运行的定时采集任务
    -> 解析、比较变化、检查完整性
    -> 发布版本化的远程 JSON / 数据存储
    -> H5 在运行时读取
```

H5 可以继续静态托管，只需另有一个能定时执行程序、写入数据的环境，例如现有服务器任务或托管的定时执行环境。无需一开始建设复杂的常驻业务后端。

关键是将资料放在可独立更新的数据地址，前端运行时读取。若把角色 JSON 直接 import 到打包产物中，更新资料仍要重新构建前端，不符合用户希望的免前端发版目标。

定时任务更新远程数据属于正常内容更新，不修改页面布局代码或用户的个人排行榜。仅依赖用户打开页面后发起抓取，可以做一次刷新，但不能保证无人访问时仍然同步，也会让来源故障直接影响访问体验，因此不作为推荐主线。

初始可采用低频同步，例如每 6 小时一次；实际频率在部署时确定。这里没有创建任何调度配置。数据更新只能跟随来源已经公开的资料，目标时效可以定义为“来源更新后，在下一次成功同步中呈现”。

## 同步程序需要处理什么

1. **发现目录变化。** 从分类树和角色目录读取条目，按稳定来源 ID 对照；保持长整数 ID 为字符串。检查返回总数与实际获取数量，不能把单页成功视为一定取全。
2. **复查旧角色。** 后补语音、皮肤或档案通常出现在已有角色详情中，不能只抓新 ID。当前目录与详情的更新日期不一致，更新时间暂只作线索。
3. **按内容判定更新。** 周期性读取详情，对需要的文字、图片链接、皮肤和音轨记录计算内容摘要；仅在内容变化时发布新数据。详情中的版本字段辅助诊断，不未经验证就作为唯一更新依据。
4. **通用解析角色内容。** 遍历组件与语种数组，提取档案图文、珍贵之物、故事、编队和海报、全部实际提供语种的音频与对应台词。皮肤需要归并跨栏目内容，不能只读取主立绘数组。
5. **区分缺项与故障。** 来源暂未提供、请求失败、结构无法识别和成功收录分别记录。空的“敬请期待”语种不算已收录；空皮肤数组也不能在抓取失败时被解释为角色没有皮肤。
6. **校验后发布。** 检查接口业务码、条目数量、必需字段、来源链接及新增媒体的可访问性。异常空列表或大面积字段丢失时停止发布，继续使用上次成功版本。
7. **保留版本与同步时间。** 数据按版本保存，发布成功后切换当前版本；保留回退能力和最近成功同步时间。缓存需有再验证或有效期，避免浏览器一直读取过期 JSON。

本次发现的分页细节：`limit=5` 被忽略，响应仍给出 `size=1000`，第一页 65 条、第二页为空；公开页面脚本也使用 `page:1,limit:1000`。未确认任意小页大小可用，不把猜测的 `pageSize` 写成已验证能力。

来源的字段及内容排版变化，需要按来源维护解析器。来源 HTML 应转换为受控图文节点或经过清理的内容，不直接执行其中脚本。

## 个人 XP 排名与资料分离

- 自动同步更新角色资料、素材、皮肤和音轨，不覆盖喜爱程度、排行顺序或个人文字。
- 新角色进入待排名集合；采集器无法替用户决定喜爱程度。
- 显示名称、目录排序、图片文件名都不作为个人排行榜的唯一关联键。
- 男女漂泊者、属性、不同形态与皮肤的关系保留。新条目关联不确定时保留独立记录，避免错误自动合并。具体排名分组属于后续产品规则。

## 高清头像的处理建议

自动更新主线使用能够按名称或来源 ID 关联的 Wiki 头像；保留已经核验的 58 条社区高清头像映射，适用时继续优先使用高清资源。攻略站为补缺来源。

未来出现新角色时，先使用可可靠关联的头像或人物图，让角色资料正常出现。社区新头像作为质量增强：能够确认关联后再提升清晰度；不把不可靠的图像相似候选直接发布成确定的角色头像。

若要求每个未来新角色都自动使用社区选择器里的最高质量图片，则还需要解决登录态获取与续期、匿名图片准确关联两个问题，维护成本明显更高。该能力目前没有得到验证。

## 难度判断

| 目标 | 判断 |
| --- | --- |
| 根据 Wiki 目录自动发现新角色、更新基础资料与图片链接 | 中低；当前匿名读取路径已验证 |
| 完整档案、全部语种、不同结构的皮肤资料持续采集 | 中等；主要工作是解析、缺项处理和不同角色的兼容 |
| 远程数据自动发布，H5 无需随版本重新发布 | 中等；需要调度、数据存储、校验、缓存和失败回退 |
| 社区新头像始终自动登录取得、准确匹配且质量最优 | 较高；存在鉴权和人物对应两项实际障碍 |
| 任意上游变化后仍然永久零维护 | 不能保证 |

建议采用“Wiki 自动同步为主、攻略站补缺、社区高清头像作为可降级增强”的方案。常规内容更新自动完成；接口规则或结构发生破坏性变化时，保留旧资料并提示维护。

完整内容的采集仍按 [MATERIAL_SCOPE.md](MATERIAL_SCOPE.md) 执行，包含必须展示的皮肤以及所有实际可取得语种的个性、战斗和皮肤专属语音。
